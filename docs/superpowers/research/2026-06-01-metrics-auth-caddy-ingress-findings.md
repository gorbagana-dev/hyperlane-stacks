# Findings: authenticating validator/relayer `/metrics` (facet 3)

**Status:** investigation only — no design chosen yet. This note records what
was verified so the design decision is grounded. It is **not** an implementation
spec.

## Background

Cross-host monitoring (facets 1 + 2) moved Prometheus from in-cluster pod
discovery to scraping each validator/relayer over its public Caddy hostname
(`validator-gorchain.bridge.gorbagana.wtf/metrics`, etc.). A side effect: those
`/metrics` endpoints are now reachable over public DNS with **no authentication**
— anyone can scrape them.

Facet 3 ("auth layer in the monitoring stack") closes that gap.

## Scope decision

The auth layer protects the **scrape endpoints** (`/metrics` on the
validator/relayer pods) — i.e. only the monitoring system should be able to read
them. The Grafana / Prometheus **UIs are out of scope** (Grafana already has its
own login; the Prometheus web UI is a separate concern). Mechanism: HTTP **basic
auth** — both ends are machines (Prometheus scrapes the agent), traffic is HTTPS
in prod, and a single shared credential is sufficient. Prometheus has native
`basic_auth` support on scrape jobs.

## Central finding: the Caddy ingress controller cannot enforce basic auth today

The deferred-auth design suspected this; it is now confirmed from source and docs.

### Caddy the *server* vs. the caddy-ingress *controller*

These are two different things, and the distinction is the whole point:

| Component | Supports basic auth? | Why |
|---|---|---|
| **Caddy web server** (Caddyfile / JSON `http.handlers.authentication`) | **Yes** | `basic_auth` is a standard Caddyfile directive in the stock distribution (renamed from `basicauth` in 2.8.0). |
| **caddy-ingress controller** (`caddyserver/ingress`, and the `LaconicNetwork/ingress` fork built on it) | **No** | The controller *generates* Caddy's JSON config from Kubernetes `Ingress` objects in Go. It only emits handlers for the annotations it knows about; none of them is auth, and it never emits the `authentication` handler. There is no Caddyfile to write a directive into. |

The `basic_auth` *handler module* is compiled into the controller's Caddy binary
(it ships with the `caddyserver/caddy/v2` dependency). But the **config that
drives that binary is owned and regenerated by the controller** — so the module
is present yet unreachable: there is no annotation, and no raw-config escape
hatch, that makes the controller put an auth handler into the config. Any manual
edit to the running config would be overwritten on the next Ingress change.

### Evidence

- **The fork is the official `caddyserver/ingress` plus cert-storage changes.**
  Its Go module path is still `caddyserver/ingress`
  (`internal/caddy/global/configmap.go` imports `caddyserver/ingress/pkg/...`).
  The `LaconicNetwork/ingress` commits are entirely `SecretStorage`/certmagic
  (storing certs in k8s Secrets) plus dependency bumps and CI — **none touch
  ingress features or annotations.** So the fork did not remove or disable auth;
  upstream simply never exposed it.
- **Full supported annotation set** (`internal/caddy/ingress/annotations.go`,
  prefix `caddy.ingress.kubernetes.io/`): `rewrite-to`, `rewrite-strip-prefix`,
  `disable-ssl-redirect`, `backend-protocol`, `insecure-skip-verify`,
  `permanent-redirect`, `permanent-redirect-code`, `temporal-redirect`,
  `trusted-proxies`. **No auth annotation.** Git history shows every one was
  added by upstream `caddyserver/ingress` PRs (#86, #103, #165, #249), not the
  fork.
- **No non-annotation path either.** The global ConfigMap plugin
  (`internal/caddy/global/configmap.go`) exposes only *structured* TLS/ACME knobs
  (CA, email, EAB, on-demand TLS, debug) — not raw Caddy handler injection.
- **Docs corroborate:** the Caddy `basic_auth` directive page describes a
  *server* directive in the standard distribution; the `caddyserver/ingress`
  controller documents no auth annotation.

### Why "the basic_auth already in Caddy" can't just be turned on

The Caddy running as the ingress controller is configured exclusively by the
controller (which pushes generated JSON via Caddy's admin API). You don't get a
Caddyfile or a knob. To use *that* Caddy's basic auth you must make the
**controller emit the handler** — a code change in the controller. The only way
to use basic auth without changing the controller is to run a **second Caddy
whose config you own** (a sidecar).

## Secret-delivery constraint (affects the Prometheus side either way)

stack-orchestrator injects secrets as **env vars only** (`secrets:` →
`envFrom.secretRef`); it does not mount secret files. Prometheus' `basic_auth`
takes an inline `password` or a `password_file`. With env-only secrets, the
password reaches the Prometheus container as an env var, so `prometheus.yml` must
be **rendered from a template at container start** (`envsubst` on a `.tmpl`) — a
pattern already used elsewhere in this repo. This is independent of where auth is
enforced.

## Ruled out: agent-native auth

The Hyperlane agent has **no built-in option to authenticate its metrics
endpoint** — checked against the agent source (a fork of hyperlane-monorepo):

- The metrics server registers `/metrics` as a plain `axum` `get` handler with
  no auth middleware (`rust/main/hyperlane-base/src/server/base_server.rs`).
- The only metrics setting is the port (`metricsPort` → `HYP_METRICSPORT`);
  `settings/base.rs` exposes `metrics_port: u16` and nothing else.
- No `auth`/`password`/`username`/`bearer`/`token` anywhere in the metrics path
  or settings.

Upstream Hyperlane serves metrics openly and expects network- or proxy-level
protection. So auth must be enforced **in front of** the agent — which is what
the options below do.

## Options

### A. Auth reverse-proxy sidecar (changes only in `hyperlane-stacks`) — recommended

Add a small Caddy sidecar to the validator/relayer pods (mirroring the existing
`kms-proxy` sidecar). It runs the **server** `basic_auth` directive and proxies
authenticated requests to `localhost:9090` (the agent metrics). The ingress route
changes from `proxy-to: validator:9090` to the sidecar's port.

```
Prometheus --https--> Caddy ingress --> auth sidecar (basic_auth) --> localhost:9090 agent
```

- **Pros:** one repo, one PR; reuses an established pattern; controller-agnostic;
  no shared-infra risk; uses the documented Caddy server directive directly.
- **Cons:** an extra container per validator/relayer pod; auth config lives
  per-pod.

### B. Expose basic auth in the caddy-ingress fork (auth at the edge)

Add a plugin to `LaconicNetwork/ingress` (the controller already has a plugin
system, upstream PR #86) that reads a new annotation and emits Caddy's existing
`caddyauth` handler; rebuild and push the controller image.

- **Blocker:** stack-orchestrator's `http-proxy` block emits only `path` +
  `proxy-to` and has **no way to put an arbitrary annotation** on the generated
  Ingress. So this spans **three repos**: the ingress fork *and*
  stack-orchestrator *and* this repo.
- **Pros:** auth centralized at the edge; no per-pod sidecar.
- **Cons:** multi-repo change + fork image release; the ingress controller is
  shared infra (blast radius); much larger coordination than a single feature PR.

### C. Network / IP allowlist (no credentials)

Restrict `/metrics` to the monitoring host's source IP.

- **Blocker:** the fork has no IP-allow annotation, and a k8s NetworkPolicy is
  ineffective here (cross-host scrapes arrive via the ingress controller, so the
  pod sees the controller's IP, not the scraper's). It would have to live at the
  cloud firewall on the ingress host.
- **Pros:** zero code, zero secrets.
- **Cons:** an ops/infra control outside these repos; coarse; depends on stable
  scraper IPs; gives no per-scraper credential.

## Recommendation

**Option A (sidecar).** It is the only option self-contained in
`hyperlane-stacks`, ships as one PR, reuses the `kms-proxy` sidecar pattern, uses
the Caddy server `basic_auth` directive as documented, and carries no
shared-infra risk — consistent with how facets 1 + 2 were built. Option B is the
cleaner edge architecture in the abstract but is a three-repo effort touching
shared infrastructure; it is worth pursuing only if exposing auth-at-edge becomes
an explicit platform goal.
